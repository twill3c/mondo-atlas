# L11 の記録 —— 足す手順が本当に効くかを、足して確かめた

loop_018。目標は「メノンをリーダーに載せ、あわせて第2層の一行要旨を全 31 頁ぶん書く」。

L10 で「篇を足すには三点が要る。忘れたら T-721 が落ちる」と書いた。
**書いただけでは効くかどうか分からない。** だから足してみた。

## 1. 足し忘れの検査は、本当に落ちた

`INCLUDE` にメノンを足してデータを作り、**頁を作らずに**テストを走らせた。

```
→ app\read\men\page.tsx が無い: expected false to be true
FAIL  T-721 目次に載る篇には、実在する頁と本文ファイルが対応する
```

**足りないファイルの名前まで出た。** これが出なければ、
メノンは目次に載っているのに開けない状態で出荷されていた。

L10 で `app/read/zzz/` を作って対照を確認したのは「余分な頁」の側で、
今回は「足りない頁」の側が実物で撃たれた。両側とも効いている。

## 2. 分割は主張どおりだった

四篇目を足しても、他の頁は重くならない。

| 道筋 | 圧縮前 |
|---|---|
| `/read/`(目次) | 17 KB |
| `/read/euthphr/` | 166 KB |
| `/read/ap/` | 279 KB |
| `/read/crit/` | 144 KB |
| **`/read/men/`(新)** | **約 200 KB** |

分割前の作りなら、四篇目を足した時点で一枚 704 KB になっていた。
**いちばん重い頁は 279 KB のまま動かない。**

直リンクも何も足さずに通った —— `?loc=Men.82b` で 82 頁が開く。
篇ごとの配線ではなく、節 ID から篇を導く仕組みにしていたからである。

## 3. 目次から未訳 ID の列を外した

メノンを足した直後、目次が 0.7 KB → **2.5 KB** に太った。
`untranslated`(未訳の節 ID の列)を持っていたので、
メノンの 151 件がそのまま入ったのである。

未訳の篇が増えるほど目次が太る —— **分割の意味が薄れる方向**なので外した。
数は `nSections` と `nTranslated` で足りるし、ID の列は篇のファイルが持っている。
目次は 0.9 KB に戻った。T-722 の上限も 4000 → 2000 バイトに締めた。

## 4. 「未訳は空欄」の経路が、実データで撃てるようになった

L9 で三篇とも完訳になり、実データから未訳が消えて対照が主語を失った。
そのとき合成した篇に移した(T-717)。
メノンが入って、**実データの側でも撃てるようになった**(T-725)。

合成の対照は**消していない**。実データがまた完訳だけになる日が来る。

検品の側も直した。それまで `/read/` の検査は
「完訳の篇なので未訳の空欄は 0」と決め打ちしていた ——
未訳の篇が載ったら、その決め打ちは**正しい表示を不合格にする**。
篇ごとに「その頁の未訳節数」を期待値として持たせ、
0 に決め打ちしていたのをやめた。対照も両側に置いた
(未訳なのに空欄が出ていない / 空欄が多すぎる)。

> 決め打ちの期待値は、正常が一種類しかないうちは通る。
> **二種類目が来た日に、正しいものを落とす。**

画面はこう出る —— 頁を選ぶ釦 31 個すべてが破線(全頁が未訳)、
三段目は `(未訳)` の斜体、断り書きは「和訳は 0 / 151 節。
訳の無い節は空欄のまま置いてある —— 節そのものが無いのではなく、まだ訳していない」。

## 5. 第2層(F-11)を 31 頁進めた

| | 頁 | 割合 |
|---|---|---|
| L6 まで(裁判三部) | 53 / 1,752 | 3.0% |
| **L11(メノンを追加)** | **84 / 1,752** | **4.8%** |

要旨は**英訳本文を一頁ぶん読んでから書いた**(L6 の規律)。
記憶や概説から書いたものは「たぶんこう書いてある」であって、要旨ではない。

書いたあと三つ検算した ——
頁番号が原文に実在すること、算用数字を本文に書いていないこと(G-07 の散文版)、
ラテン文字・キリル文字・制御文字の混入がないこと。混入は 0 件だった。

## 6. 行単位の検査では原理的に見えない故障

README にパスを書こうとして、ヒアドキュメント経由の編集で
バックスラッシュ r が**実際の復帰文字**になった。
行は `app` + CR + `ead` となり、表示上は「appead」に見える。
このセッションで五度目のバックスラッシュ事故である。

問題は `text_hygiene` が**違反 0 件を返した**ことだった。理由は二重にある。

1. CRLF のファイルでは CR 自体が正常なので、
   符号位置の集合(`ALLOWED_CONTROL`)では弾けない
2. さらに Python の万国改行は**孤立した CR も改行として扱う**ので、
   行に分けた時点で CR は消えている —— `scan_line` には届かない

つまり**行単位の検査では原理的に見えない**。除外設定の問題(HC-121)ではなく、
検査の単位が合っていなかった。

バイト列で「LF が続かない CR」を探す検査を足し、対照を両側に置いた ——
陽性(孤立 CR・末尾の CR)と陰性(CRLF・LF のみ)。
実ファイルを壊して撃てることも確かめた。

```
scratch-cr-test.md: 孤立した復帰文字(位置 9) — '見出し\r続き\n'
走査 1 ファイル / 違反 1 件
```

> 「違反 0 件」は「検査した」を意味しない。
> **検査の単位が合っていなければ、対象は最初から視野に入っていない。**
