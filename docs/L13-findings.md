# L13 の記録 —— パイドン 62 頁と、追記だけでは直せなくなったログ

loop_023(loop_022 は欠番。理由は下記)。
目標は「第2層(F-11)の一行要旨をパイドン全 62 頁ぶん書く」。

## 1. 進み具合 —— はじめて一割を超えた

パイドンは 62 頁で、これまでで最も長い。約 27,300 語を読んだ。

裁判三部に続けたので、**告発(エウテュプロン)→ 裁判(弁明)→
脱獄の拒否(クリトン)→ 最期の日(パイドン)**が日本語で通して読めるようになった。
これが今回この篇を選んだ理由である。

## 2. 目標の数字を、確かめずに書いた

`loop_start` の目標に「パイドン 46 頁」と書いた。**実測は 62 頁**である。
46 は前ループの所見に「次候補」として書いた数字で、それをそのまま持ち込んだ。

書く前に一行測れば済んだ。HC-124「下限は当てずっぽうで置かず、まず実測する」と同じ型である。

## 3. その訂正が、ログを直せなくした

数字を直そうとして、`correction` を **`loop_start` 自身**に当てた。
`append` はこれを受理する。ところが:

- 有効レコード列の先頭が `correction` になる
- → **LL-01(先頭イベントは loop_start)に違反する**
- → `correction` は `correction` を指せない(LL-08)ので、**追記だけで直す道が無い**

`append` は成功を返し、**あとから `validate` だけが落ちる**。
しかもその時点で、規範上許された操作では回復できない。

> 操作は通ったのに、その操作のせいで以後ずっと不整合 —— いちばん質の悪い失敗の形である。

根は、不変条件を守る責任を**検査側だけ**に置き、生成側(`append`)に置いていなかったこと。
**追記専用の記録では、壊せる操作を受理してから壊れを報告する設計は取り返しがつかない。**

### 直したこと

`looplog.py` の `append` が、`correction.supersedes` の指す先が `loop_start` のとき
**受理せずに拒む**ようにした。拒否メッセージで代替も案内する。

```
記録拒否 — loop_start は correction で無効化できません(LL-01 と衝突)。
  目標の書き間違いは**その旨を stage_end の notes に書いて先へ進む**か、
  作業が始まっていなければ別のループ ID で立て直してください。
```

入れたあと、**同じ操作を実際に打って拒まれることを確かめた**。

HC-150 に起票した。`looplog.py` は全プロジェクト共通なので、正本への還流が要る(未実施)。

## 4. 壊れたログは、書き換えずに畳んだ

`loop_022` は 4 行(loop_start / stage_end / correction / loop_start)しかなく、
実作業の記録は入っていなかった。二つの道があった。

1. 中身を書き換えて同じ ID を使い回す
2. 撤去して番号を飛ばし、次のループにその理由を書く

**2 を選んだ。** 書き換えると訂正の経緯が消える。欠番なら
「ここで何かがあった」が残り、`loop_023` の `loop_start` に理由を書ける。

追記専用の記録を守るために記録を一つ捨てた形で、
**「履歴を書き換えない」より「不整合を残さない」を優先した**判断である。
どちらも規範なので、どちらを取ったかを書き残しておく。
