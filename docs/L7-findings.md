# L7 の記録 —— 三段リーダーと、字が壊れていたこと

loop_009。目標は「三段リーダー(F-08)と節への直リンク(F-09)を作り切る。
完訳(F-12)は裁判三部のうち最も短いクリトン全 59 節から積む。
未訳節は原文の側から数えて画面に出す(G-06)」。

## 1. なぜクリトンから訳したか

裁判三部は 254 節ある。一ループでは終わらない。
それでも**一篇を完訳する**ことを先にしたのは、G-06(和訳の脱落検査)が
**未訳が全部の状態でも緑になる**からである。

「原文の節を並べて、訳の無いものを数える」仕組みは、
訳がひとつも無ければ「未訳 254 節」と正しく答える。正しいが、何も試していない。
**完訳が一本あって初めて「0 件」という主張が生まれ、その主張が検査される。**

結果:

| 篇 | 節 | 訳 | 状態 |
|---|---|---|---|
| エウテュプロン | 70 | 0 | 未着手 |
| ソクラテスの弁明 | 125 | 0 | 未着手 |
| クリトン | 59 | 59 | **完訳** |

充填率は**二つの分母で**出した。三篇を分母にすると 23.2%、
全集を分母にすると 0.69%。**後者が本当の進み具合**である。
画面には両方を並べてある。片方だけを出すと、どちらを選んでも読み手を誤らせる。

## 2. 未訳は「原文の側から」数える

uta-gaeshi の G-14/G-15 で学んだことをそのまま持ち込んだ ——
**訳文に何が入っているかを見ても、原文の何が落ちたかは分からない。**

`etl/build_reader.py` は原文の節を全部並べたうえで、訳の付いていない節の ID を列挙する。
`nTranslated` はその**引き算**で出す(訳の側を数えて足し上げない)。
T-702 はこの導出関係そのものを検査する。

逆向きの検算も置いた。**訳はあるが原文に無い節**があれば、それは節 ID の書き間違いである。
`build_reader.py` はそれを見つけたら exit 1 で止まる。

## 3. 目玉ではないが、いちばん時間を使ったこと —— 字が壊れていた

画面ができて、全部緑になって、写真を見た。ギリシャ語がこう出ていた。

```
πολυ`  δε`  τη`ν    ← 正しくは πολὺ δὲ τὴν
```

**アクセントが、次の字の後ろに独立した点として描かれていた。**

順に潰した。

1. **データを疑った** → 合成済み符号(U+1F7B 等)で正しい。NFC 済み。混入なし。
2. **CSS を疑った** → 指定は届いている。
3. **書体を疑った** → これだった。

指定していた Georgia は多アクセント(polytonic)ギリシャ語の合成済み符号を持たない。
ブラウザは字ごとに代替書体へ落ち、落ちた先が**アクセントを分けて描いた**。

六つ実測した。

| 書体 | 多アクセントを正しく描けるか |
|---|---|
| Georgia | ✗ |
| Palatino Linotype | ✗ |
| Times New Roman | ✗ |
| Segoe UI | ✗ |
| 既定の serif | ✗ |
| **Cambria** | **○** |

この機で通ったのは Cambria だけだった。
**読み手の機械に何が入っているかは当てにできない。**
EB Garamond を `next/font` でビルド時に取り込み、自分の配信元から出すことにした
(実行時に外へ取りに行かない)。

### この故障の性質

**代理指標は全部緑だった。** 高さも、横溢れも、要素数も、JS エラーもない。
検品が見ていたのは**字が置かれた場所**であって、**字の形**ではなかった。
`font-family` に何と書いたかは、実際に何で描かれたかを教えない ——
指定は正しく通っていて、なお字が壊れる。

見つけたのは**写真を見たとき**である。HC-041 の「目で見なければ分からない性質は
テストで代替しない」がまた当たった。

そのうえで、**次は機械で捕まえる**。Chrome に直接聞く。

```
CDP: CSS.getPlatformFontsForNode(.sec__grc) → [{familyName, glyphCount}]
```

条件は「**一節点が単一の書体で描き切られていること**」。
「大半が正しい」では通さない —— **一部の字だけ代替に落ちるのが、
まさに合成済み符号が欠けたときの壊れ方**だからである。

陽性対照も置いた。和訳の欄は別の書体で組んである。
そこまで同じ答えが返るなら、この問い合わせは書体を見ていない。

```
希語の書体 — OK(EB Garamond ひとつで 284 字すべてを描いた。対照: 和訳の欄は Yu Gothic UI)
```

HC-134 に起票した。**該当しそうな既存プロジェクト(ikari-uta / uta-gaeshi / umi-no-ki)は
本ループでは検査していない** —— 未検査であることを HC に明記した。

## 4. めくる単位を、住所の単位に合わせた

最初、リーダーは 59 節を一度に出した。検品が落とした。

| 幅 | 高さ |
|---|---|
| 390px | 48,667px |
| 768px | 23,596px |
| 1280px | 20,691px |

高さの上限は「表や列が潰れていないか」の代理指標として置いたもので、
これは潰れではなく**設計の問題**だった —— めくる単位を持たせていなかった。

閾値を上げて通すこともできたが、そうしなかった。
**ステファヌス頁をそのままめくる単位にした。**
住所の単位(`Crit.51c` の `51`)と、めくる単位が同じになる。
クリトンは 12 頁、弁明は 26 頁。頁を選ぶ釦を並べ、
**まだ訳の無い頁は破線で示す**(隠さない。訳が無いことも情報である)。

直リンクはこれに合わせて「その節を**含む頁**を開く」ようにした。
`pageIndexOf()` を足し、T-713 で全 59 節について
「返る頁にその節が入っている」ことを検査する。

## 5. 直リンクは壊れた住所で試す

`?loc=` は URL から来た文字列で、それを要素の探索にそのまま渡すわけにいかない。
`lib/reader.ts` は正規表現で形を検査し、通ったものだけを返す。

検査は**実ブラウザで、壊れた住所も含めて**やる。
通る例をいくら並べても、形の検査を素通りさせていないかは分からない。

| 住所 | 結果 |
|---|---|
| `?loc=Crit.51c` | 51 頁を開いて焦点 |
| `?loc=Crit.43a` | 43 頁を開いて焦点 |
| `?loc=Ap.17a` | 未訳の篇でも通る |
| `?loc=%3Cscript%3E` | 既定の頁に落ちる |
| `?loc=Crit.99z` | 既定の頁に落ちる(`z` は節の字ではない) |
| `?loc=Rep.327a` | 既定の頁に落ちる(形は正しいがリーダーに載せていない篇) |
| (なし) | 既定の頁 |
